Usher 第一阶段数据流水线

运行记录 · 数据快照时间：2026 年 10 月 5 日（UTC） · 所在分支：stage1-data

本文记录第一阶段数据部分的完整过程，对应实验说明的 A5 至 A9 节。流水线共有 8 个步骤。每个步骤都说明：它对应实验说明的哪一节，用哪个脚本执行，读取哪些数据，具体做了哪些处理，生成哪些文件，以及这次运行的实际情况。文中所有数字都来自 manifest/ 和 data/ 目录下由脚本生成的结果文件，没有手工填写。

如何重新运行

整条流水线由一个入口脚本 run_data.sh 按顺序执行。它有两种运行方式：

./run_data.sh            # 访问 GitHub 拉取数据，然后重新生成所有结果。拉取中断后再次运行会从中断处继续。
./run_data.sh --offline  # 不访问 GitHub，只用本地已缓存的原始数据重新生成所有结果。

只要本地存在 data/raw/ 目录，脚本就直接使用其中缓存的原始数据，不会重新拉取。如果要基于最新数据生成新的快照，需要先把 data/raw/ 目录移走。

关于哪些文件纳入 git 版本管理：data/ 目录存放原始数据和中间数据，不纳入 git。纳入 git 的有三类：脚本；manifest/ 目录，存放 issue 编号列表、文件校验值和各项统计数字；review/ 目录，存放数据报告、人工核对表，以及 AI 核对的结果和汇总。

通过已登录的 GitHub 命令行工具 gh 访问 GitHub 的 GraphQL 接口。
处理过程

拉取 microsoft/vscode 仓库中，创建时间在 2023 年 1 月 1 日至 2026 年 9 月 30 日之间的全部 issue。按创建时间从新到旧排序，每次请求取 100 条。每条 issue 记录以下字段：

  • 编号和创建时间；
  • 标题和正文；
  • 提交者的登录名，以及 GitHub 标注的账号类型（例如普通用户或 Bot）；
  • 当前带有的全部标签，每条最多取 50 个；
  • 当前的全部负责人，每条最多取 20 个；
  • 重复关系，即 GitHub 的 duplicateOf 字段。如果这条 issue 被维护者标为另一条 issue 的重复，这个字段记录那条原 issue 的编号、创建时间和所在仓库。

每次请求返回的原始数据都立即保存到本地。如果拉取中途中断，再次运行时会从上次的位置继续。如果 GitHub 返回限流错误，脚本会等待一段时间后重试。

加上参数 --flatten 运行时，脚本把所有原始数据合并成一张表，每条 issue 占一行，按编号排序。

生成文件
  • data/raw/issues_pages/：每次请求返回的原始数据。
  • data/issues.jsonl.gz：合并后的 issue 表。
  • data/pull_meta.json：拉取的开始和结束时间、拉取数量。

2.1 按创建时间切分

先按每条 issue 的创建时间，把它分到三个集合中的一个：

  • 训练集：2025 年 1 月 1 日至 2026 年 5 月 31 日创建的 issue；
  • 调参集：2026 年 6 月创建的 issue；
  • 测试集：2026 年 7 月 1 日至 9 月 30 日创建的 issue。

2025 年以前创建的 issue 不属于这三个集合，只在查重时作为可以被检索到的历史 issue 使用（见 2.5）。

切分之后、筛选之前，训练集有 56,331 条，调参集有 2,537 条，测试集有 7,966 条。

2.2 三项判断共用的筛选

以下两条规则对三项判断都适用，按顺序执行。

  • 去掉 bot 提交的 issue。bot 自动提交的 issue 不是真实用户的反馈。提交者满足以下任一条件，就认为是 bot：登录名在 PoC 代码里的已知 bot 名单中；登录名以 [bot] 结尾；或者 GitHub 把这个账号的类型标为 Bot。这一步去掉的数量是：训练集 526 条，调参集 69 条，测试集 385 条。其中有 9 条只能靠 GitHub 的账号类型识别出来。
  • 去掉正文为空的 issue。实验说明 A4 节要求每条 issue 都有正文。正文去掉空白字符后没有任何内容的 issue，在这一步去掉。去掉的数量是：训练集 593 条，调参集 23 条，测试集 44 条。

2.3 类型判断的筛选

类型标签指 vscode 官方 wiki 列出的 10 个标签，例如 bug、feature-request。只有恰好带一个类型标签的 issue 才保留，这个标签就是该 issue 类型的正确答案。去掉的有两种情况：

  • 没有任何类型标签：训练集 39,468 条，调参集 1,807 条，测试集 5,631 条。
  • 带有两个或以上类型标签，无法确定哪个是正确答案：训练集 646 条，调参集 17 条，测试集 58 条。

2.4 负责人判断的筛选

只有至少有一位负责人的 issue 才保留。如果一条 issue 有多位负责人，他们都算正确答案，模型预测出其中任何一位都算对。没有负责人而被去掉的数量是：训练集 15,451 条，调参集 402 条，测试集 968 条。

2.5 查重判断的筛选

只有被维护者标为重复、并且指向的原 issue 同时满足以下三个条件的 issue 才保留，原 issue 就是正确答案。按顺序检查，每一项去掉的数量如下：

  • 没有被标为重复（没有 duplicateOf 字段）：训练集 53,569 条，调参集 2,319 条，测试集 7,198 条。
  • 原 issue 不在 vscode 仓库，而在其他仓库：训练集 37 条，调参集 1 条，测试集 10 条。
  • 原 issue 的创建时间不早于这条 issue。这种情况下，这条 issue 提交时原 issue 还不存在，不可能被检索到：训练集 396 条，调参集 25 条，测试集 42 条。
  • 原 issue 创建于 2023 年 1 月 1 日之前，不在我们拉取的数据范围内：训练集 101 条，调参集 4 条，测试集 19 条。

查重时的检索范围：对每一条要查重的 issue，在全部 107,422 条已拉取的 issue 中，只检索创建时间比它早的那些。

2.6 标记与训练集正文完全相同的测试 issue

按照实验说明，测试集中与训练集某条 issue 正文完全相同的 issue 保留，但要做标记，以便报告时分别给出“全部测试数据”和“去掉这些 issue 之后”两个分数。

比较方法：把每条 issue 的标题和正文拼在一起，去掉正文中的 HTML 注释（issue 模板里的说明文字），正文截到 2,000 个字符，再把连续的空白合并成一个空格、全部转成小写，然后和同一项判断训练集中的每条 issue 比较是否完全相同。

结果：类型判断的测试集中有 0 条被标记，负责人判断有 9 条，查重判断有 0 条。负责人的这 9 条都是只填了模板、没有实际内容的报告，例如正文只有“bug”或一个句号。

处理过程

对负责人测试集中的每一条 issue，拉取它的完整操作记录（GitHub 称为时间线，记录了打标签、分派负责人、关闭等每一次操作），并缓存到本地。

在每条操作记录中，找到第一次由 vscode 的 bot 账号 vs-code-engineering[bot] 执行的分派操作，记下这次分派给了谁。这就是 bot 的首次分派，用来和我们的负责人判断做对照。

GitHub 的 REST 接口每小时最多允许 5,000 次请求。脚本每拉 50 条检查一次剩余的请求次数；剩余不足 200 次时，暂停到额度重置后再继续。

生成文件
  • data/raw/timelines/：每条 issue 的原始操作记录。
  • data/bot_first_assignment.json 和 manifest/bot_first_assignment.tsv：每条测试 issue 的 bot 首次分派结果。
  • data/timeline_meta.json：拉取的开始和结束时间、请求次数、覆盖情况。

第 4 步：检查最终负责人是否落实

对应说明
A9 节“评估数据质量”中负责人一项（2026 年 10 月 7 日修订）。
执行脚本
scripts/pipeline/assignee_check.py。只读取本地缓存，不访问 GitHub，离线运行时同样执行。
读取数据
第 2 步得到的负责人测试集（含每条 issue 的最终负责人）；第 3 步缓存的操作记录；第 3 步得到的 bot 首次分派结果；第 1 步的 issue 表（用来查 issue 的提交者）。
处理过程

“该分给谁”取决于团队内部分工，无法从公开信息判断对错，所以负责人一项不做主观核对，而是检查维护者最后的决定是否落实：在每条 issue 的操作记录里，找出由任何一位最终负责人执行的操作。以下记录虽然写着这个人的名字，但不是他本人的操作，不计入：被别人分派或取消分派；被别人在评论里提到（mentioned）；被 GitHub 自动加入或移出关注（subscribed、unsubscribed）。提交 issue 本身不在操作记录里，也不计入。

每条 issue 按最终负责人做过的最“强”的操作归入一类，强弱顺序和定义如下：

  • 关闭了 issue：某位最终负责人是这条 issue 的“关闭”（closed）操作的执行者。这次运行有 1,996 条（30.4%）。
  • 通过提交或 PR 关联：某位最终负责人在代码层面关联了这条 issue：提交的说明里提到了它（referenced 事件），或在一个 PR 中引用了它（来源是 PR 的 cross-referenced 事件），或把一个 PR 关联到它（connected 事件）。这次运行有 179 条（2.7%）。
  • 评论：某位最终负责人在这条 issue 下发表过评论（commented 事件）。这次运行有 452 条（6.9%）。
  • 在其他 issue 中引用：某位最终负责人在另一条 issue（不是 PR）中提到了这条 issue（来源不是 PR 的 cross-referenced 事件）。这次运行有 45 条（0.7%）。
  • 其他编辑操作：某位最终负责人做过上面以外的操作，例如加减标签、设置里程碑、修改标题、重新打开、锁定、设置 issue 类型或项目字段、标为重复，或者把这条 issue 分派给别人、取消别人的分派。这次运行有 704 条（10.7%）。
  • 只做了自我分派：最终负责人做过的唯一操作是把自己分派到这条 issue（或取消自己的分派）。这次运行有 27 条（0.4%）。
  • 没有任何操作：在时间线里找不到任何由最终负责人执行的操作。这次运行有 3,166 条（48.2%）。

此外还统计了三组子集：bot 首次分派的人在最终负责人中、不在最终负责人中、bot 没有分派过。对“没有任何操作”的 issue，还统计了它在拉取操作记录时仍然打开、被分诊 bot 关闭，还是被其他人关闭。

生成文件
manifest/assignee_check.tsv（每条 issue 的类别、做过操作的最终负责人、所属子集）和 manifest/assignee_check.json（类别定义和各项统计）。

负责人测试集 6,569 条 issue 的操作记录都可用。其中 3,403 条（51.8%）至少有一位最终负责人做过操作，3,166 条（48.2%）没有任何最终负责人的操作。在没有操作的 issue 中，2,208 条仍然打开，475 条被分诊 bot 关闭，483 条被其他人关闭。按子集分组的结果如下：

第 7 步：AI 核对类型和查重的正确答案

本步骤由 AI 模型（Claude Opus 5.5）核对，未经人工核实。

对应说明
A9 节“评估数据质量”中类型和查重两项（2026 年 10 月 7 日修订）。
执行方式
逐条阅读和判断由 AI 模型完成，结果写入 review/ai_review_type.csv 和 review/ai_review_duplicate.csv。之后由脚本 scripts/pipeline/ai_review_summary.py 统计数量和置信区间，这个脚本在离线运行时同样执行。
读取数据
第 6 步抽出的样本（每项 30 条）；第 1 步的 issue 表中的标题和正文；通过 GitHub 接口拉取的这些 issue 的评论，以及查重样本对应的原 issue 的评论，缓存在 data/review_comments/。评论是在快照之后拉取的，不属于快照，第 5 步计算校验值时跳过这个目录。
处理过程

判断标准对每一条都一样，只根据公开内容判断：

  • 类型：维护者最后的类型标签符合 issue 内容的判为“对”（例如真实的缺陷对应 bug，请求新的行为对应 feature-request）；明显属于另一种类型的判为“错”；内容太少或确实可以归入不止一种类型的判为“无法判断”。
  • 查重：这条 issue 和原 issue 描述的是同一个根本问题或同一个需求的判为“对”；明显是不同问题的判为“错”；看不清楚的判为“无法判断”。

每一条都写一句中文理由。正确率 = “对”÷（“对”+“错”），“无法判断”不计入分母，单独报告它的占比；95% 置信区间用 Wilson 方法计算，这种方法在样本少、正确率接近 100% 时仍能给出合理的区间。

生成文件
review/ai_review_type.csv、review/ai_review_duplicate.csv（列：编号、链接、正确答案、核对结果、理由）和 review/ai_review_summary.json（数量、正确率、置信区间、和 85% 标准的对比）。

与实验说明不一致的地方

  • 查重的检索范围包含 bot 提交的 issue。有 5 条测试 issue，它们的原 issue 是 bot 提交的。如果把 bot 提交的 issue 从检索范围中去掉，这 5 条就不可能被找到。因此 bot 提交的 issue 只是不作为查重的测试题目，仍然保留在检索范围内。
  • 人工核对表包含 issue 原文。核对表显示了正文的前 400 个字符，而实验说明规定公开 repo 中不放 issue 正文。发布前需要去掉这部分内容。
  • 请求额度的检查方式。GitHub 的额度查询命令 gh api rate_limit 一直返回满额，和实际消耗不符。因此改为从每次实际请求的响应头中读取剩余额度。
  • 脚本目录的名称。如果把脚本放在 scripts/data/，会被 .gitignore 中忽略 data/ 的规则一并忽略，所以脚本放在 scripts/pipeline/。
