运行记录 · 数据快照时间：2026 年 10 月 5 日（UTC） · 最近更新：2026 年 10 月 7 日 · 所在分支：stage1-data

2026 年 10 月 7 日修订：负责人判断改为模块判断。按修订后的实验说明，第一阶段的三项判断是类型、模块和查重。“模块”指一条 issue 涉及 vscode 的哪个代码区域，例如终端或编辑器标签页，在 vscode 仓库里用标签表示。原来的负责人判断停止评估，因为“该分给谁”取决于团队内部分工，无法用公开信息评估；已完成的负责人数据和检查（第 3、4 步）保留作为记录，文中标为“已停用”。

本文记录第一阶段数据部分的完整过程，对应实验说明的 A5 至 A9 节。流水线共有 8 个步骤。每个步骤都说明：它对应实验说明的哪一节，用哪个脚本执行，读取哪些数据，具体做了哪些处理，生成哪些文件，以及这次运行的实际情况。文中所有数字都来自 manifest/ 和 data/ 目录下由脚本生成的结果文件，没有手工填写。

如何重新运行

整条流水线由一个入口脚本 run_data.sh 按顺序执行。它有两种运行方式：

./run_data.sh            # 访问 GitHub 拉取数据，然后重新生成所有结果。拉取中断后再次运行会从中断处继续。
./run_data.sh --offline  # 不访问 GitHub，只用本地已缓存的原始数据重新生成所有结果。

只要本地存在 data/raw/ 目录，脚本就直接使用其中缓存的原始数据，不会重新拉取。模块标签所依据的 data/raw/classifier.json 也属于快照；联网运行时如果这个文件不存在，脚本会从 vscode 仓库下载第 2 步记录的那个提交中的版本，离线运行时只核对本地文件和记录的版本是否一致。如果要基于最新数据生成新的快照，需要先把 data/raw/ 目录移走。

关于哪些文件纳入 git 版本管理：data/ 目录存放原始数据和中间数据，不纳入 git。纳入 git 的有三类：脚本；manifest/ 目录，存放 issue 编号列表、文件校验值和各项统计数字；review/ 目录，存放数据报告、人工核对表，以及 AI 核对的结果和汇总。

处理过程

拉取 microsoft/vscode 仓库中，创建时间在 2023 年 1 月 1 日至 2026 年 9 月 30 日之间的全部 issue。按创建时间从新到旧排序，每次请求取 100 条。每条 issue 记录以下字段：

  • 编号和创建时间；
  • 标题和正文；
  • 提交者的登录名，以及 GitHub 标注的账号类型（例如普通用户或 Bot）；
  • 当前带有的全部标签，每条最多取 50 个；
  • 当前的全部负责人，每条最多取 20 个；
  • 重复关系，即 GitHub 的 duplicateOf 字段。如果这条 issue 被维护者标为另一条 issue 的重复，这个字段记录那条原 issue 的编号、创建时间和所在仓库。

每次请求返回的原始数据都立即保存到本地。如果拉取中途中断，再次运行时会从上次的位置继续。如果 GitHub 返回限流错误，脚本会等待一段时间后重试。

加上参数 --flatten 运行时，脚本把所有原始数据合并成一张表，每条 issue 占一行，按编号排序。

生成文件

  • data/issues.jsonl.gz：合并后的 issue 表。
  • data/pull_meta.json：拉取的开始和结束时间、拉取数量。

2.1 按创建时间切分

先按每条 issue 的创建时间，把它分到三个集合中的一个：

  • 训练集：2025 年 1 月 1 日至 2026 年 5 月 31 日创建的 issue；
  • 调参集：2026 年 6 月创建的 issue；
  • 测试集：2026 年 7 月 1 日至 9 月 30 日创建的 issue。

2025 年以前创建的 issue 不属于这三个集合，只在查重时作为可以被检索到的历史 issue 使用（见 2.6）。

切分之后、筛选之前，训练集有 56,331 条，调参集有 2,537 条，测试集有 7,966 条。

2.2 各项判断共用的筛选

以下两条规则对所有判断都适用，按顺序执行。

  • 去掉 bot 提交的 issue。bot 自动提交的 issue 不是真实用户的反馈。提交者满足以下任一条件，就认为是 bot：登录名在 PoC 代码里的已知 bot 名单中；登录名以 [bot] 结尾；或者 GitHub 把这个账号的类型标为 Bot。这一步去掉的数量是：训练集 526 条，调参集 69 条，测试集 385 条。其中有 9 条只能靠 GitHub 的账号类型识别出来。
  • 去掉正文为空的 issue。实验说明 A4 节要求每条 issue 都有正文。正文去掉空白字符后没有任何内容的 issue，在这一步去掉。去掉的数量是：训练集 593 条，调参集 23 条，测试集 44 条。

2.3 类型判断的筛选

类型标签指 vscode 官方 wiki 列出的 10 个标签，例如 bug、feature-request。只有恰好带一个类型标签的 issue 才保留，这个标签就是该 issue 类型的正确答案。去掉的有两种情况：

  • 没有任何类型标签：训练集 39,468 条，调参集 1,807 条，测试集 5,631 条。
  • 带有两个或以上类型标签，无法确定哪个是正确答案：训练集 646 条，调参集 17 条，测试集 58 条。

2.4 模块判断的筛选（2026 年 10 月 7 日新增）

模块标签从哪里来。vscode 仓库里有一个配置文件 .github/classifier.json，vscode 的分诊机器人用它按模块自动给 issue 分派负责人。文件的 labels 部分列出了 311 个标签，每个标签代表一个代码模块，例如 terminal（终端）、workbench-tabs（编辑器标签页）、install-update（安装和更新）。按实验说明 A7，这些标签就是模块标签。

文件的来源。我们使用的是 2026 年 10 月 3 日从 vscode 默认分支取得的副本（PoC 阶段取得，原保存在 poc/feasibility/data/classifier.json），把它复制到快照中的 data/raw/classifier.json，并像其他数据文件一样计算了校验值。为了确定它对应 vscode 的哪个版本，2026 年 10 月 7 日向 GitHub 发了一次查询，列出最近修改这个文件的提交。结果显示，我们这份副本的 git 对象编号（f38027d8…，由文件内容唯一决定）和提交 9de77c295b1bd405e4c21e3e089a8af538a0c83f（2026 年 5 月 22 日，“Add browser-integration assignment to classifier.json”）中的版本完全一致，而这个提交也是截至查询时最后一次修改该文件的提交。来源网址、取得日期、提交编号和校验值都记录在 manifest/module_labels.json 和 manifest/snapshot.json 中。脚本每次运行都会重新核对文件和这个版本是否一致。

只保留真正在用的标签。classifier.json 中可能列着仓库里已经不用的标签。快照里没有仓库的完整标签列表，所以用快照本身检查：只有在拉取到的 107,422 条 issue 中至少出现过一次的标签，才算模块标签。按这条规则保留 291 个，去掉 20 个从未出现过的标签（例如 ipc、notebook-kernel、workbench-touchbar）。从未出现过的标签不可能成为任何 issue 的正确答案，所以这条规则不影响筛选结果，只是让以后基线模型的候选模块列表更干净。作为对照，PoC 阶段用当时的仓库标签列表检查，有 298 个标签存在；我们保留的 291 个都在其中。

筛选规则。在 2.2 的两条共用规则之后，只保留至少带一个模块标签的 issue。正确答案是 issue 当前带有的全部模块标签。带多个模块标签的 issue 也保留，这些标签都算正确答案。没有任何模块标签而被去掉的数量是：训练集 46,424 条，调参集 2,190 条，测试集 6,850 条。

带多个模块标签的 issue。实验说明 B2 要求单独报告这类 issue 的占比。训练集 8,788 条中有 1,020 条（11.6%）带两个或以上模块标签，调参集 255 条中有 11 条（4.3%），测试集 687 条中有 72 条（10.5%）。测试集的这 72 条里，55 条带 2 个模块标签，15 条带 3 个，2 条带 4 个。

测试集中的模块。测试集里出现了 126 个不同的模块标签，最多的是 ux（105 条）、terminal（67 条）、browser-integration（58 条）、workbench-tabs（51 条）和 install-update（44 条）。只有一个模块标签 editor-comments 在测试集出现、但在训练集从未出现，涉及 1 条测试 issue。

已知局限：classifier.json 已经过时。这份 classifier.json 没有收录 2025 至 2026 年新增的大部分模块，尤其是聊天和智能体相关的区域（其中只有 chat-terminal 等个别与聊天有关的标签）。结果是，测试集时间段（2026 年 7 至 9 月）经过共用规则后剩下的 7,537 条 issue 中，有 6,850 条因为没有模块标签被去掉，只保留了 687 条。被去掉的 issue 中，有 2,986 条没有任何标签；其余 issue 上经常出现的 agents-window（445 条）、agent-host（284 条）、chat（76 条）都是近年大量使用、但 classifier.json 中没有的模块类标签。因此，模块测试集只覆盖 classifier.json 列出的模块，不代表这段时间的全部 issue。用它得到的分数只说明模型在这些模块上的表现，不能推广到聊天、智能体等新区域，报告分数时必须写明这一点。

2.5 负责人判断的筛选（已停用）

这一项于 2026 年 10 月 7 日停止使用，结果保留作为记录。只有至少有一位负责人的 issue 才保留。如果一条 issue 有多位负责人，他们都算正确答案，模型预测出其中任何一位都算对。没有负责人而被去掉的数量是：训练集 15,451 条，调参集 402 条，测试集 968 条。

2.6 查重判断的筛选

只有被维护者标为重复、并且指向的原 issue 同时满足以下三个条件的 issue 才保留，原 issue 就是正确答案。按顺序检查，每一项去掉的数量如下：

  • 没有被标为重复（没有 duplicateOf 字段）：训练集 53,569 条，调参集 2,319 条，测试集 7,198 条。
  • 原 issue 不在 vscode 仓库，而在其他仓库：训练集 37 条，调参集 1 条，测试集 10 条。
  • 原 issue 的创建时间不早于这条 issue。这种情况下，这条 issue 提交时原 issue 还不存在，不可能被检索到：训练集 396 条，调参集 25 条，测试集 42 条。
  • 原 issue 创建于 2023 年 1 月 1 日之前，不在我们拉取的数据范围内：训练集 101 条，调参集 4 条，测试集 19 条。

查重时的检索范围：对每一条要查重的 issue，在全部 107,422 条已拉取的 issue 中，只检索创建时间比它早的那些。

2.7 标记与训练集正文完全相同的测试 issue

按照实验说明，测试集中与训练集某条 issue 正文完全相同的 issue 保留，但要做标记，以便报告时分别给出“全部测试数据”和“去掉这些 issue 之后”两个分数。

比较方法：把每条 issue 的标题和正文拼在一起，去掉正文中的 HTML 注释（issue 模板里的说明文字），正文截到 2,000 个字符，再把连续的空白合并成一个空格、全部转成小写，然后和同一项判断训练集中的每条 issue 比较是否完全相同。

结果：类型判断的测试集中有 0 条被标记，模块判断有 0 条，查重判断有 0 条，已停用的负责人判断有 9 条。负责人的这 9 条都是只填了模板、没有实际内容的报告，例如正文只有“bug”或一个句号。

处理过程

“该分给谁”取决于团队内部分工，无法从公开信息判断对错，所以负责人一项不做主观核对，而是检查维护者最后的决定是否落实：在每条 issue 的操作记录里，找出由任何一位最终负责人执行的操作。以下记录虽然写着这个人的名字，但不是他本人的操作，不计入：被别人分派或取消分派；被别人在评论里提到（mentioned）；被 GitHub 自动加入或移出关注（subscribed、unsubscribed）。提交 issue 本身不在操作记录里，也不计入。

每条 issue 按最终负责人做过的最“强”的操作归入一类，强弱顺序和定义如下：

  • 关闭了 issue：某位最终负责人是这条 issue 的“关闭”（closed）操作的执行者。这次运行有 1,996 条（30.4%）。
  • 通过提交或 PR 关联：某位最终负责人在代码层面关联了这条 issue：提交的说明里提到了它（referenced 事件），或在一个 PR 中引用了它（来源是 PR 的 cross-referenced 事件），或把一个 PR 关联到它（connected 事件）。这次运行有 179 条（2.7%）。
  • 评论：某位最终负责人在这条 issue 下发表过评论（commented 事件）。这次运行有 452 条（6.9%）。
  • 在其他 issue 中引用：某位最终负责人在另一条 issue（不是 PR）中提到了这条 issue（来源不是 PR 的 cross-referenced 事件）。这次运行有 45 条（0.7%）。
  • 其他编辑操作：某位最终负责人做过上面以外的操作，例如加减标签、设置里程碑、修改标题、重新打开、锁定、设置 issue 类型或项目字段、标为重复，或者把这条 issue 分派给别人、取消别人的分派。这次运行有 704 条（10.7%）。
  • 只做了自我分派：最终负责人做过的唯一操作是把自己分派到这条 issue（或取消自己的分派）。这次运行有 27 条（0.4%）。
  • 没有任何操作：在时间线里找不到任何由最终负责人执行的操作。这次运行有 3,166 条（48.2%）。

此外还统计了三组子集：bot 首次分派的人在最终负责人中、不在最终负责人中、bot 没有分派过。对“没有任何操作”的 issue，还统计了它在拉取操作记录时仍然打开、被分诊 bot 关闭，还是被其他人关闭。

判断标准对每一条都一样，只根据公开内容判断：

  • 类型：维护者最后的类型标签符合 issue 内容的判为“对”（例如真实的缺陷对应 bug，请求新的行为对应 feature-request）；明显属于另一种类型的判为“错”；内容太少或确实可以归入不止一种类型的判为“无法判断”。

每一条都写一句中文理由。正确率 = “对”÷（“对”+“错”），“无法判断”不计入分母，单独报告它的占比；95% 置信区间用 Wilson 方法计算，这种方法在样本少、正确率接近 100% 时仍能给出合理的区间。

与实验说明不一致的地方

以下各条是实际做法和实验说明的文字不完全一致、或者实验说明没有写明而我们自行决定的地方。

  • 查重的检索范围包含 bot 提交的 issue。有 5 条测试 issue，它们的原 issue 是 bot 提交的。如果把 bot 提交的 issue 从检索范围中去掉，这 5 条就不可能被找到。因此 bot 提交的 issue 只是不作为查重的测试题目，仍然保留在检索范围内。
  • 人工核对表包含 issue 原文。核对表显示了正文的前 400 个字符，而实验说明规定公开 repo 中不放 issue 正文。发布前需要去掉这部分内容。
  • 请求额度的检查方式。GitHub 的额度查询命令 gh api rate_limit 一直返回满额，和实际消耗不符。因此改为从每次实际请求的响应头中读取剩余额度。
  • 模块标签多了一条“必须在用”的限制。实验说明 A7 只说模块标签是 classifier.json 中列出的模块。我们另外要求标签在快照的 issue 中至少出现过一次，去掉了 20 个从未使用的标签（见 2.4）。这条限制不改变任何 issue 的筛选结果，只缩小了模块的候选列表。
  • classifier.json 用的是当前版本，不是历史版本。A2 提到第二阶段需要 classifier.json 的历史版本。本阶段只用一个版本（2026 年 5 月 22 日的提交，截至查询时仍是最新版本）来确定哪些标签是模块标签，没有按 issue 的创建时间使用当时的版本。
  • 脚本目录的名称。如果把脚本放在 scripts/data/，会被 .gitignore 中忽略 data/ 的规则一并忽略，所以脚本放在 scripts/pipeline/。

A 部分小结

A 部分的任务是准备第一阶段要用的数据，并检查数据质量是否达到实验说明 A4 的标准。这里先解释几个反复用到的词。训练集、调参集、测试集是按 issue 创建时间切出的三份数据：训练集（2025 年 1 月至 2026 年 5 月）让模型学习规律，调参集（2026 年 6 月）用来调整模型设置，测试集（2026 年 7 月至 9 月）只在最后打分时用一次。正确答案是我们从维护者的操作中提取、用来给模型打分的标准答案，例如维护者最后打上的标签。A4 标准要求正确答案确实正确的比例不低于 85%，数据中不含 bot 提交的 issue，每条 issue 都有正文和创建时间。正确答案核对是从每项判断的测试集中随机抽 30 条，由 AI 模型（Claude Opus 5.5）根据 issue 的公开内容逐条判断正确答案对不对，结果未经人工核实。95% 置信区间表示考虑到只抽了 30 条，真实的正确率大致落在的范围；样本越少，区间越宽。

后两条 A4 标准对三项判断都满足：bot 提交的 issue 和正文为空的 issue 已在筛选中去掉，创建时间由 GitHub 记录，每条都有。下表汇总三项判断的数据量和正确答案核对结果。

判断训练集调参集测试集核对结果（对 / 错 / 无法判断）正确率与 95% 置信区间与 A4 对比
类型15,0986211,84828 / 0 / 2100.0%（87.9% 至 100.0%）达标，区间下限也不低于 85%
模块8,78825568730 / 0 / 0100.0%（88.6% 至 100.0%）达标，区间下限也不低于 85%
查重1,1099626827 / 1 / 296.4%（82.3% 至 99.4%）按正确率达标，但区间下限低于 85%

正确率的算法是“对”的条数除以“对”和“错”的条数之和，“无法判断”不计入。三项判断的正确率都不低于 85%，按 A4 都可以用来出结果。需要始终说明的是，这些核对都由 AI 模型完成，未经人工核实。

类型

类型判断回答“这条 issue 是缺陷、功能需求还是其他类型”，正确答案是维护者最后打上的那个类型标签。筛选后训练集 15,098 条、调参集 621 条、测试集 1,848 条。核对的 30 条中 28 条判为“对”，没有判为“错”的；2 条判为“无法判断”，都是既可以看作缺陷、也可以看作界面打磨或功能变更的情况。正确率 100.0%，95% 置信区间 87.9% 至 100.0%，达到 A4 标准。

已知局限有三点。第一，只有恰好带一个类型标签的 issue 才能进入数据，很多 issue 没有任何类型标签（测试集时间段内经过共用规则后的 7,537 条中，有 5,631 条、约 74.7% 因此被去掉），所以类型数据只代表维护者打过类型标签的那部分 issue。第二，类型分布很不均匀：测试集 1,848 条中 bug 有 1,224 条、feature-request 有 487 条，其余八种类型加起来只有 137 条，有几种只有 1 到 5 条，所以按类型分别计算再平均的 macro-F1 分数会很不稳定。第三，核对只有 30 条，区间仍有十几个百分点宽。

模块

模块判断回答“这条 issue 属于 vscode 的哪个代码模块”，正确答案是 issue 当前带有的全部模块标签，模块标签指 vscode 仓库 classifier.json 中列出、并在快照中实际用过的 291 个标签。筛选后训练集 8,788 条、调参集 255 条、测试集 687 条。带两个或以上模块标签的 issue 在测试集中占 10.5%（72 条），在训练集中占 11.6%（1,020 条）；这些 issue 的每个模块标签都算正确答案。核对的 30 条全部判为“对”，其中 4 条是多模块 issue，每个标签都与 issue 有关。正确率 100.0%，95% 置信区间 88.6% 至 100.0%，达到 A4 标准。

最重要的局限是 classifier.json 已经过时。它对应 2026 年 5 月 22 日的提交，没有收录 2025 至 2026 年新增的大部分模块，尤其是聊天和智能体相关的区域，例如 agents-window、agent-host、chat。因此测试集时间段内经过共用规则后的 7,537 条 issue 中，有 6,850 条因为没有模块标签被去掉，模块测试集只剩 687 条，而且只覆盖 classifier.json 列出的模块。用它得到的分数只能说明模型在这些模块上的表现，不能推广到聊天、智能体等新区域，也不能代表这段时间的全部 issue。核对中也看到了这个问题：有几条 issue 的标签本身没有错，但 issue 的主体其实是聊天或智能体，标签只覆盖了其中一部分。其他局限是：调参集只有 255 条，带多个模块标签的只占 4.3%，和训练集、测试集差别较大；测试集中有 1 个模块（editor-comments）在训练集中从未出现，模型不可能学到它。

查重

查重判断回答“这条 issue 是否重复了以前的某条 issue”，正确答案是 GitHub 的 duplicateOf 字段记录的那条更早的原 issue。筛选后训练集 1,109 条、调参集 96 条、测试集 268 条。核对的 30 条中 27 条判为“对”，1 条判为“错”，2 条判为“无法判断”。正确率 96.4%，95% 置信区间 82.3% 至 99.4%。按正确率本身达到 A4 标准，但区间下限低于 85%，也就是说只凭这 28 条有结论的样本，还不能排除真实正确率略低于标准的可能。

已知局限有三点。第一，测试集只有 268 条，以后报告 recall@1、recall@5、recall@10 等分数时，置信区间会比另外两项宽。第二，只用了 duplicateOf 字段：很多重复 issue 只被打上重复标签、没有记录原 issue 是哪条，这些 issue 无法用来打分，不在数据里。第三，判为“无法判断”的 2 条显示，同一版本发布后集中出现的崩溃常被合并到同一个 issue 下，即使症状并不完全相同，这是查重正确答案最容易出偏差的地方；判为“错”的 1 条则是两条公开内容看不出联系的 issue 被标为重复。另外，检索范围保留了 bot 提交的 issue，因为有 5 条测试查询的原 issue 是 bot 提交的。

负责人（已停用）

负责人判断已于 2026 年 10 月 7 日停止评估，由模块判断取代，原因是“该分给谁”取决于团队内部分工，无法用公开信息判断对错，而且检查发现负责人测试集 6,569 条中有 3,166 条（48.2%）的最终负责人从未在 issue 上做过任何操作；相关数据和检查结果保留作为记录。
