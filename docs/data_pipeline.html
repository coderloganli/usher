第 1 步：批量拉取 issue（说明 A5）

命令
scripts/pipeline/pull_issues.py，再执行一次加 --flatten
输入
GitHub GraphQL 接口（通过已登录的 gh）
做了什么
按创建时间从新到旧，每页 100 条，拉取 2023-01-01 至 2026-09-30 创建的全部 vscode issue。每条记录编号、创建时间、标题、正文、作者（登录名和账号类型）、最终标签（最多 50 个）、最终负责人（最多 20 个）、重复关系 duplicateOf（原 issue 的编号、创建时间、所在仓库）。原始页面逐页存盘，中断后可从上次位置继续；遇到限流会等待重试。--flatten 把所有页面合并成每条 issue 一行的表。
输出
data/raw/issues_pages/（原始页面）；data/issues.jsonl.gz（合并后的表）；data/pull_meta.json（拉取时间和数量）

第 2 步：筛选和切分（说明 A7、A8）

命令
scripts/pipeline/build_sets.py
输入
data/issues.jsonl.gz
做了什么
  1. 按创建时间把 issue 分到训练集（2025-01-01 至 2026-05-31）、调参集（2026-06）、测试集（2026-07-01 至 2026-09-30）。
  2. 三项判断都先去掉 bot 提交的 issue（规则：登录名在 PoC 的 bot 名单里，或以 [bot] 结尾）。
  3. 类型：只保留恰好带一个类型标签的（类型标签是 vscode wiki 列出的 10 个），这个标签就是正确答案。
  4. 负责人：只保留至少有一位负责人的，全部最终负责人都算正确答案。
  5. 查重：只保留 duplicateOf 指向 vscode 仓库、原 issue 比它早创建、且原 issue 创建于 2023-01-01 之后的；原 issue 就是正确答案。查重的检索范围是全部 107,422 条中早于该 issue 创建的。
  6. 标记测试集里和同一判断训练集正文完全相同的 issue（标题加正文，去掉 HTML 注释，正文截到 2,000 字符，合并空白、转小写后比较），保留不删。
输出
data/sets.json（完整集合，不进 git）；manifest/sets/<判断>_<集合>.tsv（编号和正确答案）；manifest/counts.json（各集合数量、每条规则去掉的数量、标记情况）

第 3 步：拉取测试集时间线（说明 A5）

命令
scripts/pipeline/pull_timelines.py（离线重建时加 --extract-only）
输入
负责人测试集的 issue 编号（来自第 2 步）；GitHub REST 接口
做了什么
逐条拉取负责人测试集 issue 的完整操作记录，缓存到本地。从中找出第一个由 vs-code-engineering[bot] 执行的分派事件，记下 bot 首次分派的负责人。每拉 50 条检查一次剩余请求额度（从实际请求的响应头读取），剩余不足 200 次时等到额度重置。
输出
data/raw/timelines/（原始操作记录）；data/bot_first_assignment.json 和 manifest/bot_first_assignment.tsv；data/timeline_meta.json
本次运行
2026-10-05 04:12:45 至 05:26:18（1 小时 13 分钟，其中约 7 分钟在等额度重置），6,615 次请求，6,604 条全部拉到。其中 4,264 条（64.6%）有 bot 的首次分派。这一步在第 1 步拉完 7–9 月数据后就开始了，第 1 步全部完成后测试集没有变化。

第 4 步：存档（说明 A6）

命令

做了什么

输出
manifest/snapshot.json、manifest/issue_numbers.txt、manifest/issue_hashes.tsv、manifest/checksums.sha256

第 5 步：生成人工核对表（说明 A9）

命令
scripts/pipeline/review_sheet.py
做了什么
每项判断从测试集随机抽 30 条（随机种子 20261004）。每条显示 issue 链接、标题、正文前 400 个字符和正确答案；查重还显示原 issue 的链接和标题。每条可选“对 / 错 / 无法判断”并写备注，填写内容保存在浏览器里，每组可导出 CSV。判断栏全部留空。
输出
review/review_sample.json（抽中的编号）；review/review_sheet.html

  • 正文为空的 issue：质量标准（A4）要求每条都有正文，但筛选规则（A7）没写去掉它们，所以暂时保留，只做了统计。测试集中类型 16 条、负责人 29 条、查重 0 条；训练集中分别为 186、349、3 条。待决定是否去掉。
  • bot 识别规则的漏网：有 9 条保留下来的 issue，GitHub 把作者账号类型标为 Bot，但按说明里的规则没有识别出来。待决定是否把账号类型也纳入规则。
  • 查重的检索范围包含 bot 提交的 issue：有 5 条测试 issue 的原 issue 是 bot 提交的。bot 提交的 issue 只排除在测试题目之外，仍然可以被检索到。
  • 人工核对表含 issue 原文：发布到公开 repo 前要去掉正文。
  • 请求额度的检查方式：gh api rate_limit 返回的额度一直是满的，和实际不符，改为从实际请求的响应头读取。
  • 脚本目录名：scripts/data/ 会被 .gitignore 里的 data/ 规则忽略，所以脚本放在 scripts/pipeline/。
