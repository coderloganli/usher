Usher stage 1: baseline results

Part B of stage 1 · generated by scripts/baselines/report.py from outputs/baselines/ · ground truth reviewed by an AI model (Claude Opus 5.5), not human-verified

Usher is an issue-triage agent for the public microsoft/vscode repository. It makes three judgments for each new issue: its type (for example bug or feature request), the code module it belongs to, and whether it duplicates an earlier issue. This page reports simple, standard methods that use no large language model. They are the baselines: a later method counts as an improvement only if it beats them.

  • Type. Learning from words beats always guessing bug, but the two goals conflict. The model tuned for accuracy is right on 79.4% of test issues; the model tuned for macro-F1 (which weights every type equally) is right on only 63.5%, no better than always guessing bug (66.2%).   • Duplicate. Embedding retrieval puts the true original among its first 10 candidates for 38.8% of test queries, about twice as often as BM25 (19.0%). For 152 of 268 queries neither method finds the original in its first 10.

2. How the baselines were built and measured

2.1 Data

The data come from Part A of stage 1 (see docs/data_pipeline.html): a snapshot of all 107,422 issues created 2023-01-01 to 2026-09-30, filtered and split by creation time. Training data teach the models, tune data are used to choose settings, and test data are used once at the end.

Every method reads the issue title and the raw body. HTML comments in the body are kept, because some of them record which issue template the reporter chose, which is known when the issue is created (section 3.3). The ground truth is the maintainers' final type label, the issue's module labels, and GitHub's duplicateOf link. A sample of 30 test issues per judgment was checked by an AI model (Claude Opus 5.5); this check is not human-verified. No test issue has text identical to a training issue, so every score is reported once.

2.2 Methods

JudgmentMethodWhat it doesSetting

For a duplicate query the candidates are all snapshot issues created before it. If several candidates score the same as the true original, the original is counted as ranked last among them.

2.3 Choosing settings before the test

Logistic regression has two settings that must be chosen: the regularization strength C (smaller is more cautious) and whether rare classes get more weight. Ten combinations were trained on the training set and scored on the tune set. For type, the combination with the best tune macro-F1 and the combination with the best tune accuracy differ, so both were kept as baselines. Neither duplicate method learns from data, so the 1,205 train and tune queries were used as development data. A third method, reciprocal rank fusion of the two rankings (RRF, k = 60), was tried there and dropped by a rule fixed in advance: it had to beat the better single method on recall@10 with a 95% paired interval above zero, and it did not (+1.1 points (-1.1 to +3.2)). Section 6 lists every development score.

2.4 Scores and uncertainty

Each 95% confidence interval comes from a bootstrap: the test issues are drawn again with replacement 10,000 times (fixed seed 20261007) and the score is recomputed each time; the middle 95% of these scores is the interval. Two methods are compared on the same resampled issues (a paired bootstrap). A difference counts as significant when its interval does not include zero. Macro-F1 averages the F1 score over the types that appear in the truth or the predictions, with equal weight per type.

7. Limitations

  • The ground truth was checked on 30 test issues per judgment by an AI model, not by a person.
  • Type covers only issues that carry exactly one type label; most issues carry none.
  • Module covers only the modules listed in vscode's classifier.json, which lacks most chat and agent areas added in 2025–2026; the scores do not describe those areas.
  • Several types have fewer than 10 test issues, so macro-F1 and the per-type scores for them are unreliable.
  • Duplicate covers only issues linked with GitHub's duplicateOf field; the test set has 268 queries, so its intervals are wide.

8. Reproduction

From the stage1-data directory:

uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -r requirements.txt
./run_data.sh             # Part A: pull the issues from GitHub (needs the gh CLI), filter and split;
                          # use --offline instead to rebuild from an existing data/raw/ cache
./run_baselines.sh        # tuning, development, one-shot test evaluation, this report

A fresh pull returns the issues as they are on the day of the pull, so labels changed since the 2026-10-05 snapshot can change some numbers; manifest/issue_hashes.tsv shows which issues differ.

Outputs: outputs/baselines/ holds the tuning and development records, every test prediction (*_test_predictions.json), all metrics (test_metrics.json) and the error-analysis numbers (error_analysis.json). These files contain issue numbers, labels and scores only, no issue text.
