Usher 第一阶段数据报告（A5–A9）

本页由 scripts/pipeline/report.py 根据结果文件自动生成，页面里的数字都来自脚本输出，没有手工填写。

这份报告对应实验说明（stage1_spec.html）里 A5 到 A9 的数据部分：从 GitHub 拉取 microsoft/vscode 的 issue，固定成一个快照，按规则筛选，按创建时间切成训练集、调参集和测试集，并准备人工核对表。基线模型（B 部分）不在本页范围内，会在下一步完成。

报告中的“issue”指 GitHub 上的问题报告；“正确答案”指我们从维护者的操作中提取、用来给模型打分的标准答案；“bot”指自动操作的账号，例如 vscode 团队自己的分诊机器人 vs-code-engineering[bot]。

1. 快照信息

issue 数据通过 GitHub 的 GraphQL 接口一次性批量拉取，每页 100 条，按创建时间从新到旧翻页。拉取从 2026-10-05T04:09:07Z（UTC）开始，到 2026-10-05T04:54:19Z 结束，用时 45 分钟，共请求 1,078 页。创建时间在 2023-01-01 到 2026-09-30 之间的 issue 共有 107,422 条。每条 issue 记录了编号、创建时间、标题、正文、提交者、最终标签、最终负责人，以及 GitHub 的 duplicateOf 字段（这条 issue 被维护者标为哪条 issue 的重复，以及那条原 issue 的创建时间和所在仓库）。

标签每条最多取 50 个，负责人每条最多取 20 位。实际超出上限、因而可能被截断的 issue 数量是：标签 0 条，负责人 0 条。

测试集的操作记录（时间线）通过 REST 接口逐条拉取，第一条在 2026-10-05T04:12:45Z 拉取，最后一条在 2026-10-05T05:26:18Z 拉取，前后历时 1 小时 13 分钟，共 6,615 页请求（时间线超过 100 条事件的 issue 需要翻页）。时间线和 issue 不是在同一时刻拉取的，两者之间 issue 本身可能又有变化，但我们只从时间线里读 bot 的第一次分派，这一事件在之后不会改变。

快照的存档放在 manifest/ 目录：snapshot.json 记录拉取时间和查询语句；issue_numbers.txt 是全部 107,422 个 issue 编号；issue_hashes.tsv 给每条 issue 的内容（标题、正文、标签、负责人、重复关系等）算了一个校验值，别人重新拉取后可以逐条比对哪些 issue 和我们的不同；checksums.sha256 记录了 data/ 下全部 7,688 个数据文件的 SHA-256 校验值（一种文件“指纹”，内容只要改动一个字节，校验值就会完全不同）。存档时间是 2026-10-05T05:37:07Z。

5. bot 第一次分派的覆盖情况

说明 A2 要求找出 vscode 的分诊 bot（vs-code-engineering[bot]）第一次把 issue 分给了谁，留到基线阶段和我们的负责人判断做对照。做法是：拉取负责人测试集每条 issue 的时间线，取第一个由这个 bot 发出的 assigned（分派）事件，记下被分派的人。

负责人测试集共有 6,604 条 issue，其中 6,604 条成功拉到了时间线，0 条拉不到（例如 issue 已被删除或转移）。在全部 6,604 条中，有 4,264 条（64.6%）找到了 bot 的第一次分派；其余 issue 的时间线里没有这个 bot 发出的分派事件（通常是维护者直接分派的）。bot 分派得对不对，留到基线阶段再统计。结果保存在 manifest/bot_first_assignment.tsv。

7. 人工核对

核对表在 review_sheet.html。每项判断从测试集里随机抽了 30 条（随机种子 20261004），抽到的编号保存在 review/review_sample.json。表里已经列好每条 issue 的链接、标题、正文开头约 400 个字符和正确答案，判断一栏留空，需要你逐条选择“对”“错”或“无法判断”。输入会自动保存在浏览器里，核对完请用每一节的“导出 CSV”按钮导出结果。核对结果出来之后，再计算每项的正确率和置信区间，并和 A4 的 85% 标准对比。

注意：核对表里含有 issue 正文的片段。实验说明规定公开 repo 里不放 issue 正文，所以发布前需要把核对表换成只含编号和核对结果的版本。

8. 如何重新运行

在 worktree 根目录执行下面这条命令，就会依次完成拉取、筛选与切分、时间线拉取、存档、核对表和本报告。拉取脚本可以中断后续跑：已经拉到的页面和时间线会缓存在 data/raw/ 里，不会重复请求。这次快照拉取 issue 用了 45 分钟，拉取时间线用了 1 小时 13 分钟（REST 接口每小时限 5,000 次请求，脚本在额度不足时会自动等待到额度重置）。

因为拉取结果会被缓存，在已有 data/raw/ 的情况下再次运行这条命令不会重新拉取，而是在同一个快照上重新计算，结果和本页完全一致（已核对过两次运行的校验值相同）。如果要拉一个新的快照，需要先删掉或移走 data/raw/ 目录。

./run_data.sh

如果只想在已有数据上重新筛选和生成报告，不再请求 GitHub，可以运行 ./run_data.sh --offline。
