7. 模块标签（2026-10-07 新增）

模块判断是什么。模块判断回答“这条 issue 属于哪个代码模块”，例如终端（terminal）、编辑器标签页（workbench-tabs）。它在 2026-10-07 的修订中取代了负责人判断。正确答案是 issue 当前带有的全部模块标签；一条 issue 带多个模块标签时，这些标签都算正确答案，模型猜中其中任何一个都算命中（实验说明 B2 用 top-1 和 top-3 命中率打分）。

哪些标签算模块标签。vscode 仓库的 .github/classifier.json 在 labels 下列出了 311 个标签，它们是分诊机器人按模块自动分派时使用的标签。快照里没有仓库的完整标签列表，所以我们用快照本身检查这些标签是否真的在使用：只有在拉取到的 107,422 条 issue（2023-01 至 2026-09）中至少出现过一次的标签才算模块标签。按这条规则保留 291 个，去掉 20 个从未出现过的标签：bisect-ext, editor-insets, extension-prerelease, github-authentication, intellisense-config, ipc, lcd-text-rendering, merge-editor-workbench, notebook-builtin-renderers, notebook-commenting, notebook-getting-globaltoolbar, notebook-getting-started, notebook-kernel, notebook-keybinding, notebook-math, notebook-minimap, notebook-multiselect, notebook-rendering, notebook-serverless-web, workbench-touchbar。从未出现过的标签不可能成为正确答案，去掉它们只会缩小基线模型的候选范围。完整列表在 manifest/module_labels.json。

8. 类型、模块和查重：正确答案核对

本节的核对由 AI 模型（Claude Opus 5.5）完成，未经人工核实。

为什么改由 AI 核对。实验说明 A9 在 2026-10-07 修订：类型、模块和查重三项的“正确答案”是否正确，只需要根据 issue 的公开内容就能判断，人和模型掌握的信息相同，所以改由 AI 模型逐条核对，并在结果中注明。原先的人工核对表保留在 review_sheet.html（已加入模块一节），可以随时用来做人工复核。

样本。每项从测试集中随机抽 30 条（随机种子 20261004），编号保存在 review/review_sample.json，抽样在核对之前就已固定。每项判断各用一个以同一种子初始化的随机数生成器抽样，所以加入模块一项后，类型和查重的样本没有变化。

核对方法。对每条样本，模型阅读快照中的标题和正文；查重一项同时阅读原 issue 的标题和正文。正文不足以判断时再参考 GitHub 上的评论。为了做法一致，全部样本以及查重样本对应的原 issue 的评论都通过 GitHub 接口统一拉取了一次，缓存在 data/review_comments/。这些评论是在快照之后拉取的，不属于快照，也不计入快照的校验值。判断标准如下，对每一条都按同样的标准执行：

  • 类型：如果维护者最后打上的类型标签符合 issue 的内容，判为“对”，例如真实的缺陷对应 bug，请求新的行为对应 feature-request；如果内容明显属于另一种类型，判为“错”；如果内容太少，或者确实可以归入不止一种类型，判为“无法判断”。
  • 模块：如果 issue 当前的模块标签所代表的代码区域确实与 issue 描述的问题或需求有关，判为“对”；带多个模块标签时，只有每个标签都与 issue 有关才判为“对”；如果某个标签明显与 issue 无关，判为“错”；如果看不清楚，判为“无法判断”。标签“有关”但不是最具体的选择，或者 issue 的主体落在 classifier.json 没有列出的区域（例如聊天、智能体）时，仍判为“对”，并在理由中写明。
  • 查重：如果这条 issue 和它被标为重复的原 issue 描述的是同一个根本问题或同一个需求，判为“对”；如果明显是不同的问题，判为“错”；如果看不清楚，判为“无法判断”。

每一条都写了一句理由，完整结果在 review/ai_review_type.csv、review/ai_review_module.csv 和 review/ai_review_duplicate.csv，汇总数字在 review/ai_review_summary.json。模块样本中带多个模块标签的有 4 条，其中判为“对”的 4 条。

正确率的算法。正确率 = “对”的条数 ÷（“对”的条数 + “错”的条数），“无法判断”的条目不计入分母，但单独报告它占全部样本的比例。95% 置信区间用 Wilson 方法计算。置信区间表示：考虑到只抽了 30 条，真实的正确率大致落在这个范围内。Wilson 方法在样本少、正确率接近 100% 时仍然给出合理的区间，而常见的“正确率 ± 1.96 × 标准误”在这种情况下会给出超过 100% 或宽度为零的区间。

9. 负责人（已停用）：最终决定是否落实

负责人判断已于 2026-10-07 停止评估，由模块判断取代。本节的检查是停用前完成的，结果保留作为记录，也是停用的依据之一：“该分给谁”取决于团队内部分工，无法用公开信息评估，而且下面的数字显示，很多最终负责人从未在 issue 上做过任何操作。之后 agent 给出的建议负责人由我们假定的“模块 → 负责人”对应表给出，只作演示，不报告准确率。

为什么不做主观核对。一条 issue 该分给谁，取决于 vscode 团队内部的分工，从公开信息无法判断对错。因此按 2026-10-07 修订的实验说明 A9，负责人的正确答案就定义为维护者最后的决定，不再核对它“对不对”，而是检查这个决定是否落实：最终负责人有没有在这条 issue 上实际做过操作。这一项不适用 A4 中“正确率不低于 85%”的标准，只报告落实的比例。

怎么检查。脚本 scripts/pipeline/assignee_check.py 读取负责人测试集全部 6,569 条 issue 已缓存的时间线（时间线是 GitHub 对一条 issue 上每一次操作的记录，包括评论、关闭、加标签、分派等，每条记录都写明是谁做的），找出由任何一位最终负责人执行的操作。以下几类记录虽然也写着这个人的名字，但不是他本人的操作，所以不计入：被别人分派或取消分派（assigned/unassigned，执行者是别人）；被别人在评论里提到（mentioned）；被 GitHub 自动加入或移出关注（subscribed/unsubscribed）。打开 issue 本身不是时间线里的记录，所以提交 issue 也不算一次操作。

每条 issue 只归入一类：按下表从上到下的顺序，取任何一位最终负责人做过的最“强”的那种操作。例如一条 issue 的负责人既评论过、又关闭了它，就归入“关闭了 issue”。时间线缺失的 issue 有 0 条。逐条结果保存在 manifest/assignee_check.tsv，汇总在 manifest/assignee_check.json。

11. 如何重新运行

在 worktree 根目录执行下面这条命令，就会依次完成拉取、筛选与切分、时间线拉取、负责人落实检查、存档、核对表、AI 核对结果的汇总和本报告。拉取脚本可以中断后续跑：已经拉到的页面和时间线会缓存在 data/raw/ 里，不会重复请求。这次快照拉取 issue 用了 45 分钟，拉取时间线用了 1 小时 13 分钟（REST 接口每小时限 5,000 次请求，脚本在额度不足时会自动等待到额度重置）。

因为拉取结果会被缓存，在已有 data/raw/ 的情况下再次运行这条命令不会重新拉取，而是在同一个快照上重新计算，结果和本页完全一致（已核对过两次运行的校验值相同）。如果要拉一个新的快照，需要先删掉或移走 data/raw/ 目录。

./run_data.sh

如果只想在已有数据上重新筛选和生成报告，不再请求 GitHub，可以运行 ./run_data.sh --offline。模块标签列表只读取快照中的 data/raw/classifier.json，并核对它和记录的提交版本一致；负责人落实检查只读取已缓存的时间线，AI 核对的汇总只读取 review/ 下已保存的核对结果，两者在离线模式下都可以重新运行；AI 核对本身（逐条阅读和判断）不是脚本的一部分，重新运行不会改变核对结果。
